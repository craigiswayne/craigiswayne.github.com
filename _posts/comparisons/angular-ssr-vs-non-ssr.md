| Feature                            | SSR (Server-Side Rendering)                                                                                                                   | CSR (Client-Side Rendering / "Not SSR")                                                                                                             |
|:-----------------------------------|:----------------------------------------------------------------------------------------------------------------------------------------------|:----------------------------------------------------------------------------------------------------------------------------------------------------|
| **Initial Page Load**              | **Faster.** The server sends fully rendered HTML. The user sees the content immediately, even on slow connections.                            | **Slower.** The user sees a blank white screen or a loading spinner while the browser downloads and executes the JavaScript bundle to build the UI. |
| **SEO (Search Engines)**           | **Excellent.** Search crawlers (Google, Bing) see the full content immediately. Essential for public-facing content.                          | **Okay to Poor.** Google can run JS, but it's slower. Many other crawlers ignore JS-heavy sites, resulting in empty indexed pages.                  |
| **Social Media Sharing**           | **Works perfectly.** Links shared on Twitter, Facebook, or Slack will show the correct title, description, and image cards (Open Graph tags). | **Fails.** Scrapers usually do not run JavaScript, so shared links often show just the domain name or a blank preview.                              |
| **Server Load & Cost**             | **Higher.** The server must use CPU power to render the HTML for every request. Requires a Node.js environment.                               | **Lower.** You simply host static files (HTML, JS, CSS) on a CDN. The rendering work is offloaded to the user's device.                             |
| **User Experience (Slow Devices)** | **Better.** A user on an old phone sees the article/data immediately while the interactive scripts load in the background.                    | **Worse.** The user stares at a white screen until their slow phone processes the heavy JavaScript bundle.                                          |
| **Development Complexity**         | **Higher.** You need to handle server-specific issues (e.g., `window` is undefined on the server) and manage the build process.               | **Lower.** Standard Angular development. You only worry about the browser environment.                                                              |
| **Caching**                        | **Complex.** You cache generated HTML on the server or CDN. Requires strategy (e.g., cache busting, TTL).                                     | **Simple.** You cache the static JS/CSS bundles forever.                                                                                            |
| **Internal API**                   | Can host your endpoints by modifying the server.ts                                                                                            | nope                                                                                                                                                |
